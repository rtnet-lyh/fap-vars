# 점검 스크립트 작성 가이드

이 문서는 `inspection_cases_bundle`의 점검 케이스를 처음 작성하는 사람이 원천 자료 작성부터 Codex CLI 활용, replay 검증, live mode 단일 테스트까지 따라 할 수 있도록 정리한 교육용 가이드다.

## 0. 개요와 목적

점검 스크립트 작성 흐름은 원천 Markdown을 먼저 정리하고, 그 내용을 기준으로 replay 가능한 케이스 디렉터리를 만든 뒤, replay mode에서 로직을 검증하고, 필요할 때만 live mode로 실제 테스트 대상에서 확인하는 순서로 진행한다.

```text
raw_data/*.md
  -> inspection_cases/<domain>/<platform_or_product>/<case_name>/
       ├── case.json
       ├── script.py
       ├── replay.json
       ├── outputs/*
       └── result.json
  -> replay 검증
  -> live mode 단일 케이스 테스트
```

각 파일의 역할은 다음과 같다.

| 파일 | 역할 | 작성 방식 |
| --- | --- | --- |
| `raw_data/<domain>/<platform_or_product>/*.md` | 점검 항목의 원천 자료. 점검 내용, 명령어, 출력 예시, 임계치, 판단기준을 담는다. | 사람이 먼저 읽고 이해할 수 있게 작성한다. |
| `case.json` | 점검 입력값, credential placeholder, item metadata, threshold를 담는다. | 기존 유사 케이스를 복사해 필요한 값만 바꾼다. |
| `script.py` | 실제 점검 로직. 명령 실행, 출력 파싱, threshold 판정, 결과 메시지를 담당한다. | `BaseCheck` 기반으로 작성한다. |
| `replay.json` | `script.py`가 실행할 명령과 그 명령의 fixture 응답을 순서대로 담는다. | `matcher_value`를 실제 명령 문자열과 맞춘다. |
| `outputs/*` | 긴 stdout, stderr fixture를 분리해 저장한다. | 긴 출력은 `replay.json`에 직접 넣지 않는다. |
| `result.json` | `replay_cli.py` 실행 결과 산출물이다. | 수동 편집하지 않고 replay 실행으로 갱신한다. |
| `summary.json` | 디렉터리 단위 replay 실행 결과 요약이다. | 필요한 경우에만 replay 실행으로 갱신한다. |

일반적인 새 케이스 작업 범위는 `raw_data/`와 `inspection_cases/` 안에서 끝난다. `inspection_runtime/`은 여러 케이스가 함께 쓰는 실행 엔진이므로, 런타임 버그나 공통 helper 추가가 명확한 경우가 아니면 수정하지 않는다.

## 1. raw_data를 작성하는 방법

### 1.1 위치와 파일명

새 원천 자료는 `inspection_cases_bundle/raw_data/<domain>/<platform_or_product>/` 아래에 둔다. 도메인과 플랫폼은 기존 구조를 우선 따른다.

| 대상 | 예시 위치 |
| --- | --- |
| Rocky 서버 | `inspection_cases_bundle/raw_data/server/rocky/rocky_memory_usage_free_check.md` |
| Windows 서버 | `inspection_cases_bundle/raw_data/server/windows/windows_cpu_usage_counter_check.md` |
| Solaris 서버 | `inspection_cases_bundle/raw_data/server/solaris/solaris_memory_usage_vmstat_check.md` |
| NX-OS 장비 | `inspection_cases_bundle/raw_data/network/nx_os/mds_c9148s/1_1_cpu.md` |
| WebtoB | `inspection_cases_bundle/raw_data/web/webtob/rocky/webtob_process_status_top_grep_check.md` |
| NetBackup Appliance | `inspection_cases_bundle/raw_data/backup/veritas/netbackup_appliance_5240/1_1_catalog.md` |

Rocky 서버 계열은 lowercase snake case를 사용한다.

```text
rocky_<영역>_<detail>_<command>_check.md
```

다른 도메인은 기존 파일명 패턴이 섞여 있으므로 같은 제품, 장비, OS의 가까운 예시를 먼저 찾고 그 형식을 따른다. 명시적인 rename 요청이 없으면 기존 파일명 체계를 바꾸지 않는다.

### 1.2 필수 heading

raw_data 파일은 가능한 한 아래 한국어 heading 구조를 유지한다.

- `# 영역`
- `# 세부 점검항목`
- `# 점검 내용`
- `# 구분`
- `# 명령어`
- `# 출력 결과`
- `# 설명`
- `# 임계치`
- `# 판단기준`

기본 템플릿은 다음과 같다.

```markdown
# 영역
MEMORY

# 세부 점검항목
메모리 사용률

# 점검 내용
메모리 사용률 확인

# 구분
권고

# 명령어
free

# 출력 결과
               total        used        free      shared  buff/cache   available
Mem:        15726928     5016052     2362220      249868     8993692    10710876
Swap:        8060924      799920     7261004

# 설명
- available 비율이 낮으면 메모리 부족으로 성능 저하가 발생할 수 있다.
- swap 사용률이 높으면 메모리 증설 또는 불필요한 프로세스 정리가 필요하다.

# 임계치
min_available_memory_percent
max_swap_usage_percent

# 판단기준
임계치 기반
```

### 1.3 좋은 작성 예시

좋은 raw_data는 스크립트 작성자가 바로 구현할 수 있을 정도로 명령과 판단 근거가 구체적이다.

```markdown
# 영역
DISK

# 세부 점검항목
파일시스템 사용률

# 점검 내용
마운트된 파일시스템의 사용률이 기준 이하인지 확인

# 구분
필수

# 명령어
df -P

# 출력 결과
Filesystem     1024-blocks     Used Available Capacity Mounted on
/dev/root         52403200 20961280  31441920      40% /
/dev/sdb1        104806400 94325760  10480640      90% /data

# 설명
- Capacity가 기준을 초과한 파일시스템은 로그 증가, 데이터 적재, 백업 실패 원인을 확인한다.
- 임시 파일 삭제나 용량 증설 계획을 검토한다.

# 임계치
max_filesystem_usage_percent

# 판단기준
각 마운트 포인트의 Capacity가 max_filesystem_usage_percent 이하이면 정상
```

이 예시는 명령 문자열, 출력 형식, 확인할 컬럼, threshold key, 정상 기준이 모두 드러난다. 이후 `script.py`는 `df -P`를 실행하고 `Capacity` 값을 파싱해 `max_filesystem_usage_percent`와 비교하면 된다.

### 1.4 나쁜 작성 예시

아래처럼 작성하면 Codex나 작성자가 판단 로직을 추측해야 한다.

```markdown
# 영역
DISK

# 세부 점검항목
디스크 확인

# 점검 내용
디스크 상태를 본다

# 구분
필수

# 명령어
df

# 출력 결과
정상 출력

# 설명
문제 있으면 조치

# 임계치
적당히

# 판단기준
정상이면 양호
```

문제점은 다음과 같다.

- 어떤 옵션을 붙인 명령인지 모호하다.
- 실제 출력 예시가 없어 parser를 만들 수 없다.
- threshold key가 변수명으로 사용할 수 없는 값이다.
- 정상, 실패, 경고 조건이 구분되지 않는다.
- 운영자가 결과 메시지를 보고 무엇을 조치해야 하는지 알기 어렵다.

### 1.5 raw_data 작성 체크리스트

- 같은 도메인, 제품, OS의 기존 파일을 먼저 확인했는가?
- 파일명이 기존 패턴과 맞는가?
- 필수 heading이 모두 있는가?
- `# 명령어`의 문자열이 실제 실행 가능한 조회성 명령인가?
- `# 출력 결과`가 대표적인 정상 또는 비정상 예시를 충분히 담는가?
- 출력의 공백 정렬이 의미 있으면 그대로 보존했는가?
- `# 임계치` 값이 `min_available_memory_percent`처럼 안정적인 식별자인가?
- `# 판단기준`에 정상, 실패, 경고 조건이 구체적으로 적혀 있는가?
- 운영 credential, token, password, 개인키 원문이 들어가지 않았는가?

## 2. raw_data를 작성하고 Codex CLI를 활용해서 스크립트를 작성하는 방법

### 2.1 Codex CLI 실행 방식

저장소 루트는 `/home/fap/projects/fap-vars`로 지정한다. `codex-cli 0.136.0` 기준으로 `-C`는 작업 디렉터리를 지정하는 옵션이다.

대화형으로 요청할 때:

```bash
codex -C /home/fap/projects/fap-vars "inspection_cases_bundle/raw_data/server/rocky/rocky_memory_usage_free_check.md와 유사한 구조로 새 raw_data 초안을 작성해줘."
```

비대화형으로 한 번에 실행할 때:

```bash
codex exec -C /home/fap/projects/fap-vars "inspection_cases_bundle/raw_data/server/rocky/rocky_memory_usage_free_check.md를 참고해서 새 replay 케이스를 작성하고 단일 replay까지 검증해줘."
```

검토만 받고 파일을 고치지 않게 할 때:

```bash
codex exec -C /home/fap/projects/fap-vars "inspection_cases_bundle/inspection_cases/server/rocky/rocky_memory_usage_free_check를 리뷰해줘. 파일은 수정하지 말고 문제점과 테스트 갭만 알려줘."
```

운영 데이터에 쓰는 작업, live 접속, credential 갱신, 대량 산출물 재생성은 프롬프트에 명시적으로 허용하지 않는 한 요청하지 않는다.

### 2.2 raw_data 작성 요청 프롬프트 예시

새 원천 자료만 만들 때는 runtime이나 replay case 생성을 요청하지 않는다.

```text
inspection_cases_bundle/raw_data/AGENTS.md 규칙을 따라 raw_data 파일만 작성해줘.

대상:
- 도메인: server
- 플랫폼: rocky
- 점검 항목: 파일시스템 inode 사용률
- 명령어: df -Pi
- 정상 기준: inode 사용률이 85% 이하
- threshold key: max_inode_usage_percent

요구사항:
- 먼저 inspection_cases_bundle/raw_data/server/rocky의 유사 파일을 찾아 형식을 맞춰줘.
- 새 파일은 inspection_cases_bundle/raw_data/server/rocky/rocky_disk_filesystem_inode_df_check.md에 작성해줘.
- 필수 heading은 # 영역, # 세부 점검항목, # 점검 내용, # 구분, # 명령어, # 출력 결과, # 설명, # 임계치, # 판단기준을 모두 포함해줘.
- 실제 credential, token, password는 넣지 마.
- runtime, replay case, result.json은 만들지 마.
```

### 2.3 replay 케이스 생성 요청 프롬프트 예시

raw_data가 준비된 뒤에는 기존 유사 케이스를 먼저 찾게 하고, 표준 파일 세트를 생성하도록 요청한다.

```text
inspection_cases_bundle 규칙에 맞춰 새 replay 점검 케이스를 작성해줘.

원천 자료:
- inspection_cases_bundle/raw_data/server/rocky/rocky_disk_filesystem_usage_df_check.md

요구사항:
- 먼저 inspection_cases_bundle/inspection_cases/server/rocky에서 가장 유사한 케이스를 찾아 구조와 코딩 스타일을 맞춰줘.
- 새 케이스 디렉터리는 inspection_cases_bundle/inspection_cases/server/rocky/rocky_disk_filesystem_usage_df_check로 만들어줘.
- case.json, script.py, replay.json, outputs/*를 작성해줘.
- 긴 stdout은 outputs/df.stdout처럼 파일로 분리해줘.
- result.json은 수동으로 만들지 말고 replay_cli.py 실행 결과로 생성해줘.
- threshold_list[].name과 script.py의 get_threshold_var(...) 키를 반드시 일치시켜줘.
- replay.json의 matcher_value와 script.py의 실제 명령 문자열을 반드시 일치시켜줘.
- 별도 연결 상태체크 명령은 넣지 말고, 실제 점검 명령의 명령 실패, 파싱 실패, 정책 실패를 구분해서 반환해줘.
- replay 검증은 단일 케이스만 실행해줘.
- live mode는 실행하지 마.
```

### 2.4 생성 대상 파일 세트

새 replay 케이스는 보통 다음 구조를 만든다.

```text
inspection_cases_bundle/inspection_cases/<domain>/<platform_or_product>/<case_name>/
├── case.json
├── script.py
├── replay.json
├── result.json
└── outputs/
    └── <command>.stdout
```

각 파일 작성 기준은 다음과 같다.

- `case.json`: `inspection_code`는 유일하게 잡고, `item.threshold_list[].name`은 raw_data의 `# 임계치`와 맞춘다.
- `script.py`: `BaseCheck`를 상속하고 `CHECK_CLASS = Check`를 둔다.
- `script.py`: 화면에 보이는 `metrics`, `message`를 사람이 판단할 수 있는 수준으로 채운다. `fail`은 `error` 값도 짧고 명확하게 잡는다.
- `script.py`: SSH는 `_ssh(...)`, Windows PowerShell은 `_run_ps(...)`, 대화형 네트워크 장비는 `_run_paramiko_commands(...)` 패턴을 우선 검토한다.
- `replay.json`: 배열 형태로 작성하고, 일반 명령은 `matcher_type: exact`를 기본으로 둔다.
- `outputs/*`: 긴 stdout 또는 stderr를 저장한다.
- `result.json`: replay 실행으로 생성한다.

### 2.5 Codex 결과 검토 체크리스트

Codex가 파일을 만든 뒤에는 아래 항목을 직접 확인한다.

- 기존 유사 케이스의 구조와 디렉터리 위치를 따랐는가?
- `case.json`의 `inspection_code`가 중복되지 않는가?
- `case.json`의 threshold key와 `script.py`의 `get_threshold_var(...)` key가 같은가?
- `script.py`가 별도 연결 상태체크 명령을 중복 실행하지 않고, 실제 점검 명령의 명령 실패, 파싱 실패, 정책 실패를 구분하는가?
- 정상/경고 결과에 화면 표시용 `metrics`, `message`가 충분히 들어가는가?
- 실패 결과에 화면 표시용 `error`, `metrics`, `message`가 충분히 들어가는가?
- `replay.json`의 엔트리 순서가 `script.py`의 명령 실행 순서와 같은가?
- `replay.json`의 `matcher_value`가 실제 명령 문자열과 완전히 같은가?
- 긴 출력이 `outputs/*`로 분리되어 있는가?
- `result.json`과 `summary.json`을 수동 편집하지 않았는가?
- 실제 credential, token, password, 개인키 원문이 파일에 남아 있지 않은가?

## 3. replay_cli.py를 가지고 live mode로 테스트하는 방법

### 3.1 replay mode 선검증

live mode를 실행하기 전에는 반드시 replay mode로 단일 케이스를 먼저 검증한다.

저장소 루트에서 실행하는 예:

```bash
python3 inspection_cases_bundle/inspection_runtime/replay_cli.py inspection_cases_bundle/inspection_cases/server/rocky/<case_name>
```

번들 루트에서 실행하는 예:

```bash
python3 inspection_runtime/replay_cli.py inspection_cases/server/rocky/<case_name>
```

확인 항목:

- CLI가 오류 없이 종료되는가?
- `result.json.results[].status`가 기대와 같은가?
- `failed_items`가 의도와 같은가?
- `metrics`에 화면에서 확인할 판정 근거와 적용 기준이 들어 있는가?
- `message`를 운영자가 읽고 상태를 이해할 수 있는가?
- 실패 결과라면 `error`가 실패 유형을 짧고 명확하게 말하는가?
- `REPLAY_MISS`가 발생하지 않는가?

`REPLAY_MISS`가 발생하면 보통 `replay.json`의 `matcher_value`나 엔트리 순서가 `script.py`의 실제 명령 실행과 맞지 않는 것이다.

### 3.2 live mode 기본 원칙

live mode는 실제 테스트 대상에 접속해 명령을 실행한다. 따라서 안전 기준을 먼저 고정한다.

- live mode는 단일 케이스 디렉터리에만 실행한다.
- 운영 장비보다 테스트 장비를 우선 사용한다.
- 명령은 조회성 read-only 명령만 사용한다.
- 파일 삭제, 서비스 재시작, 설정 변경, DB 쓰기, credential 갱신 명령은 넣지 않는다.
- 운영 credential, token, password, 개인키 원문을 `case.json`, `replay.json`, `outputs/*`, 문서에 남기지 않는다.
- live mode 실행 전 replay mode가 먼저 성공해야 한다.
- live mode 실행 후 `result.json`에 secret이 섞였는지 확인한다.

분류 디렉터리나 전체 `inspection_cases`에는 live mode를 실행하지 않는다.

나쁜 예:

```bash
python3 inspection_cases_bundle/inspection_runtime/replay_cli.py --mode live inspection_cases_bundle/inspection_cases
python3 inspection_runtime/replay_cli.py --mode live inspection_cases/server/rocky
```

### 3.3 live mode 단일 케이스 실행

저장소 루트에서 실행하는 예:

```bash
python3 inspection_cases_bundle/inspection_runtime/replay_cli.py --mode live inspection_cases_bundle/inspection_cases/server/rocky/<case_name>
```

번들 루트에서 실행하는 예:

```bash
python3 inspection_runtime/replay_cli.py --mode live inspection_cases/server/rocky/<case_name>
```

실행 전에 확인할 값:

- `case.json`의 접속 대상이 테스트 장비인가?
- `case.json`의 credential 값이 커밋 가능한 placeholder인가, 아니면 로컬 테스트용으로만 임시 주입되는 값인가?
- `script.py`의 명령이 조회성인가?
- timeout, 권한, shell 종류가 대상 장비와 맞는가?
- 동일 케이스의 replay mode 결과가 이미 정상인가?

### 3.4 결과 확인

live mode 실행 후에는 `result.json`을 확인한다.

```bash
python3 -m json.tool inspection_cases_bundle/inspection_cases/server/rocky/<case_name>/result.json
```

중점 확인 항목:

- `status`: 기대한 정상, 실패, 경고 상태인가?
- `metrics`: 실제 장비 출력에서 계산한 값과 적용 기준이 들어 있는가?
- `message`: 현장 운영자가 바로 이해할 수 있는가?
- 실패 결과라면 `error`: 실패 유형이 짧고 명확한가?
- 내부 `stdout`, `stderr`, `raw_output`: secret을 포함하지 않는가?

secret 포함 여부는 최소한 아래처럼 검색한다.

```bash
rg -n 'password|token|secret|비밀번호|토큰' inspection_cases_bundle/inspection_cases/server/rocky/<case_name>
```

검색 결과가 모두 안전한 안내 문구나 placeholder인지 확인한다. 실제 값이 보이면 즉시 제거하고, 필요한 경우 테스트 credential을 교체한다.

### 3.5 live mode 후 정리

live mode가 끝나면 변경 파일을 확인한다.

```bash
git status --short
```

의도한 변경만 남겨야 한다.

- 새 케이스를 만든 작업이면 `case.json`, `script.py`, `replay.json`, `outputs/*`, replay로 생성한 `result.json`이 포함될 수 있다.
- 단일 케이스 replay만 실행했다면 해당 케이스의 `result.json`만 바뀌는 것이 일반적이다.
- 분류 단위 replay를 실행했다면 관련 `summary.json`이 바뀔 수 있다.
- 문서만 작성한 작업이면 replay, live mode, unittest는 실행하지 않는다.

최종 공유 시에는 변경 범위, 실행한 검증 명령, 실행하지 않은 검증과 그 이유를 함께 적는다.
